# 03. Legacy Architecture

## Legacy architecture

The legacy process is a scheduled, file-based enrollment workflow. It moves data across specialized tools before FACETS receives the final keyword file.

### Processing flow

1. A federal or external source places an 834 file in a monitored folder.
2. An EDI job converts the 834 transaction into a proprietary format.
3. An ECA job processes each member and assigns a benefit plan.
4. A .NET process generates the keyword file.
5. TTK and Linux jobs move files and run Bash validations.
6. W2K loads the keyword file into the FACETS core platform.

Tidal schedules and coordinates the jobs. SSIS and DataStage support loading and transformation activities.

### Operational limitations

The workflow depends on sequential file handoffs. Each tool maintains separate logs and operational controls. Database contention can delay jobs or create lock-related failures. Single-machine processing limits available parallelism.

The proprietary intermediate format complicates reuse and analysis. Operational data is optimized for FACETS loading, not broad analytics.

### Modernization boundary

FACETS remains the downstream system of record in this prototype. The modernization focuses on ingestion, transformation, validation, and data delivery.
