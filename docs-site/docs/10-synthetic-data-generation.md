# 10. Synthetic 834 Data Generation

No production member data is used anywhere in this project. All 834 files
are generated by
[`generator/synthetic_834_generator.py`](https://github.com/yourusername/medenroll834/blob/main/generator/synthetic_834_generator.py),
which produces structurally valid X12 834 (5010) EDI files from randomized
but realistic name/address/plan pools.

## Reference data pools

The generator draws from hard-coded, realistic-looking pools so the output
resembles production data in shape without being production data:

```python
FIRST_NAMES = ["JOHN", "JANE", "ROBERT", "MARY", ...]       # 38 names
LAST_NAMES  = ["SMITH", "JOHNSON", "WILLIAMS", ...]          # 38 names
STREET_NAMES = ["MAIN ST", "OAK AVE", "PINE RD", ...]
CITIES = ["NEW YORK", "LOS ANGELES", "CHICAGO", ...]         # 20 cities
STATES = ["AL", "AK", "AZ", ..., "WY"]                       # all 50
PLAN_CODES = ["100", "101", "102", "103", "104", "105", "106", "107"]  # plain numeric plan codes
RELATIONSHIP = ["18", "01", "03", "19"]  # self, spouse, child, domestic_partner
ADR_TYP = ["HOME", "MAILING", "BILLING", "WORK"]
GROUP_NUMBERS = [str(3300 + i) for i in range(50)]  # pure-numeric employer group pool
```

`PLAN_TIER_NAME` maps each numeric `PLAN_CODE` to a display tier
(`"100" -> "GOLD"`, `"101" -> "SILVER"`, ...) for `PLAN_NAME` synthesis in
Silver/Gold/OLAP, since the plan code itself is now opaque. `PLAN_CODES`
is the exact set `DataFrameValidator.VALID_PLANS`
validates against in Silver — generated files are guaranteed valid by
construction unless `--messy` is passed (see below).

## X12 envelope construction

Each file is a properly-terminated X12 interchange: `ISA` → `GS` → `ST` →
(member segments) → `SE` → `GE` → `IEA`, with a computed ISA checksum:

```python
def _checksum_isa(isa_segment: str) -> str:
    total = sum(ord(c) for c in isa_segment)
    return f"{total % 256:02d}"

def build_isa(ctrl: str, file_date: str) -> str:
    body = (
        f"*00*          *00*          "
        f"*ZZ*SENDERID     *ZZ*RECEIVERID   "
        f"*{file_date}*1200*^*00501*{ctrl}*0*T*:"
    )
    checksum = _checksum_isa(body)
    return f"ISA{body}{checksum}"
```

Segments are `~`-terminated, with a trailing newline for readability — the
`~` is the real X12 record delimiter; newlines are cosmetic (and the
Bronze parser's `split_segments()` normalizes both, see
[Chapter 13](13-bronze-layer.md)):

```python
return "\n".join(s + "~" for s in [isa, gs] + segments + [se, ge, iea]) + "\n"
```

## Member, subscriber, and group identifiers

All business identifiers are now plain-digit numeric strings instead of
prefixed codes (e.g. `"2043434"` for a member, `"3341"` for an employer
group), matching the `dbdiagram` physical models under
`docs-site/docs/assets/architecture/physical-oltp` and `physical-olap`:

```python
def _numeric_id(used: set, low: int = 1000000, high: int = 9999999) -> str:
    """Unique 7-digit member/subscriber identifier, e.g. "2043434"."""
    while True:
        candidate = random.randint(low, high)
        if candidate not in used:
            used.add(candidate)
            return str(candidate)
```

Each subscriber is assigned a `GRGR_NUM` drawn from the fixed `GROUP_NUMBERS`
pool (`"3300"`–`"3349"`) and carried through the file via the X12-standard
`REF*1L*<group number>` (Group or Policy Number) segment — the same segment
Silver's `_extract_ref_group_data()` reads back out, so `group_id` is
populated from real file content end-to-end instead of a hardcoded default:

```python
def build_ref_group(grgr_num: str) -> str:
    return f"REF*1L*{grgr_num}"
```

## Generating a batch

```python
def generate_batch(
    output_dir: str,
    num_files: int = 10,
    subscribers_per_file: int = 100,
    dependents_per_sub: int = 2,
    start_date: Optional[date] = None,
    messy: bool = False,
) -> list:
    ...
```

CLI usage:

```bash
python -m generator.synthetic_834_generator \
  --output 10_data/raw/ \
  --files 10 \
  --subs 100 \
  --deps 2
```

Or via the installed console script (`pyproject.toml` →
`[project.scripts]`):

```bash
medenroll834-generate --output 10_data/raw/ --files 3 --subs 50 --deps 2
```

Generated filenames follow `enrollment_<YYYYMMDD>_<NNN>.834`, one file per
day going backward from `start_date` (defaults to today).

## `messy` mode

Passing `--messy` intentionally introduces malformed records (missing
required fields, out-of-range dates, invalid plan codes) so the
[Silver layer's validation rules](16-data-quality-reject-handling.md) and
the [quarantine path](16-data-quality-reject-handling.md) have something
real to catch during testing — without this flag, synthetic data is
constructed to always pass validation.
